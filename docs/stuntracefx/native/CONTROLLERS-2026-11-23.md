## How the chain works
host_pad_read(index) per host (E host.h:169) -> engine eng_input_sample (E engine/input.c:205-222) polls indices 0..7 every update, copies into nshvc_input.controller[p] (on, style, buttons, lx/ly/rx/ry, lt/rt) -> game controls_read (G input/controls.c:485) claims owners -> pad[2] -> pause_update/input_read (G system/main.c:39-47, system/frame.c:12).
The engine does no dead zone, no mapping, no stable id, no connect/disconnect event. "index" = whatever the host returns for slot n.

## ISSUE 13: ways an XInput pad gives the game nothing, ranked by fit to "not detected at all"
1. **Pad is not player 1, so menus and 1P race ignore it** (best fit). controls.c:497-502: a controller becomes player 1's only if no other controller claimed first; the next distinct one becomes player 2's. Menus read only pad[0]/menu_pressed[0] (frame.c:25-27 uses frame_menu_pressed = player 1); the 1P race reads pad[0]. Anything that appears as an earlier engine controller index and shows a "fresh" bit first steals player 1: Steam Input's virtual XInput pad (Steam running, even if game not launched from Steam), DS4Windows/ViGEm/x360ce/vJoy virtual pads, a second real pad, a headset/wheel exposing XInput. The 8BitDo then is controller[1] = player 2 and nothing is shown. Even with no thief: claim only happens on a "fresh" press (below), and nothing on screen says "controller connected / press a button / you are player N".
2. **Phantom controller with a resting bit** claims player 1 on update 1. controller_state (controls.c:467-483) counts any button bit and stick past 0.5 as state; claim = now & ~ctl_was (initial 0). A device reporting a permanently set bit (virtual pad, mis-mapped axis; on Linux a non-pad /dev/input/jsN) takes player 1 without being touched and, if its stick rest is past 0.5, `used` (controls.c:504) stays 1 forever and steering is held. Real pad = player 2.
3. **Slot compaction re-indexes pads, owner is by index.** E host/windows host_windows.c:578-584: index n = nth *connected* XInput slot. Pad in slot 0 unplugged -> pad in slot 1 becomes engine controller 0. Game keeps owner[0]=0 (controls.c:491 only clears when `on` goes false for that index), so player 1's controls move to the other physical pad and the pad that was player 2 loses its owner (owner[1]=1 -> off -> -1) and must be re-claimed, but cannot claim as player 1 while owner[0] is set. Same design on macOS/iOS (GCController.controllers order, not stable) and Android (single pad).
4. **Hot-plug of the pad after launch**: Windows DOES pick it up (polled each update). Only the claim rule above matters. (Linux does not, see E-L1.)
5. **Build lacks XInput DLL**: unlikely. CMakeLists.txt:92 links `xinput9_1_0`; implicit import, -static only for the C runtime. xinput9_1_0.dll is a core System32 component on Windows 7/8/10/11 (N editions included, it is not in the Media Feature Pack); if it were missing the exe would not start at all, not "run without pad". Low rank. UNVERIFIED on a clean machine: ask Jeff to confirm with `dumpbin /imports` / Dependencies on the 0.991 exe.
6. **Pad not an XInput device at all**: 8BitDo Pro 2 in D (DInput) or S (Switch) mode, or Bluetooth modes that present as HID, is invisible on Windows (XInput only). The reporter says X mode, but it is the first thing to check (switch position/boot combo, USB vs BT: BT X-mode behaviour on Windows varies by firmware/Windows build).
7. Steam: Steam Input configured for the game (or global controller settings) can replace/hide the pad or add the virtual pad of item 1.
8. Not a cause: XInput works without window focus; sticks need no dead zone for the 0.5 thresholds; Start=MENU bit 7 and Select=BACK bit 6 map right for an XInput Pro 2.

## GAME-SIDE FINDINGS
G1. controls.c:497-502 ownership only by first fresh bit, claim never shown, player 2's pad can never become player 1's while player 1's index is still `on`. Fix: show "Player N: <controller name>" feedback (nshvc_controller_name) when claimed; let the pause screen / menus accept ANY controller for confirm/navigation when owner[0] is not in use (menus read the OR of all controllers, race keeps ownership); when exactly one real pad is present always make it player 1.
G2. controls.c:491-492 + 467-483: no stale/phantom handling. Fix: claim only on a real press (button bit or stick crossing from <0.5 to >0.5, ignore bits already set when the controller first appeared, i.e. seed ctl_was with the controller's state on the update it turns `on`, currently first appearance with any bit set counts as fresh); ignore a controller whose bits never return to zero for N seconds.
G3. controls.c:491 owner is an engine index, not an identity. Fix needs engine identity (E-1); until then: when `on` count or `nshvc_controller_name` of owner index changes, drop both owners.
G4. controls.c:132-139 and 467-480: stick thresholds fixed 0.5 with no hysteresis: a stick at 0.5 flutters (fresh each crossing, re-claims `used`). Add hysteresis (on 0.5 / off 0.35). Trigger buttons (bits 10/11) and right stick can't be claimed or used for steering: fine but a pad whose d-pad is the Linux hat (see E-L5) only works through button bits.
G5. controls.c:116: for player 1 (index 1) with owner[1] < 0 the label is looked up on controller 0, i.e. player 1's pad names are shown for player 2's bindings (pause screen). Fix: return "" when owner[player] < 0.
G6. controls.c:464 / pause.c:1167-1175: ctl_press for the rebind is taken from raw `in->controller[c].buttons` (no stick), ok; but p.ctl_last is reset only on slot change, so a pad swapped by re-indexing (G3) presses whatever it holds. Same root as G3.
G7. system/main.c:38 `system_stopped()` returns before controls_read, so ctl_was is stale after a stop; any held bit counts fresh afterwards. Minor.
G8. frame.c menus: only player 1's pad is read (frame_menu_pressed). Combined with G1 this is why a pad owned as player 2 does nothing in every menu except the pause screen (pause.c:1165-1186 reads both players: that is why issue 9's pause screen answered).

## ENGINE-SIDE FINDINGS (general defects / general missing features)
E-W1. Windows reads XInput only (host_windows.c:572-619, link line CMakeLists.txt:92). DualShock/DualSense, Switch Pro, 8BitDo D/S modes, generic HID/DInput pads are never seen. General missing feature: a second backend (Windows.Gaming.Input/RawInput+HID with a gamepad mapping DB, or a GameInput/WGI path) feeding the same host_pad, or at minimum a documented "XInput only".
E-W2. host_windows.c:578-584 compaction (see issue item 3). General fix: host_pad_read should return a stable slot (XInput user index) not "nth connected", and the engine should expose a per-pad identity (slot/GUID/name hash) that changes only when the device does.
E-W3. host_windows.c:578-584 + engine input.c:205: 8 indices x up to 4 XInputGetState each = up to 32 calls per update, 28 of them on empty slots with one pad. Polling empty XInput slots every frame is documented to be slow on some systems (xinput1_3/9_1_0 do a driver round trip). Not measured; Jeff can time `SRFX_PROFILE=1` with no pad on Windows. Fix: poll each of the 4 slots once per update, rescan disconnected slots about once a second.
E-W4. host_windows.c:594-597 y/ry clamp is wrong way round for ry (clamps `>1`, value range is -1..1.00003, harmless) and y lacks the upper clamp. Cosmetic.
E-W5. No dead zone anywhere in the engine (XInput gives raw; drifting pads read 0.1-0.2 at rest). The game's 0.5 threshold hides it, but a general engine feature is a per-axis dead zone (XINPUT_GAMEPAD_LEFT_THUMB_DEADZONE 7849 / RIGHT 8689 / TRIGGER 30), since games get raw -1..1.
E-W6. Trigger-as-button threshold 127/255 vs 0.5 on mac: ok, consistent.
E-L1. host_linux.c:564-575 `tried` is set once per index: a pad plugged after the first poll of that index never appears (no hot-plug), a pad unplugged leaves the fd open, read() fails with ENODEV forever, `on` stays 1 with the last state frozen (stuck buttons/stick, owner never released). Fix: inotify on /dev/input or retry open every second; on read error other than EAGAIN close and mark gone.
E-L2. host_linux.c:565-: /dev/input/jsN is the legacy joydev. Needs the joydev module (absent on some distros/containers) and permissions; any js node (accelerometers, some mice/tablets, virtual pads) counts as a pad (the phantom of issue item 2). Prefer evdev + a mapping DB, or at least filter by ABS_X/BTN_GAMEPAD capability.
E-L3. host_linux.c:575-585 button map `{0,1,2,3,4,5,6,7,7,8,9,7}` and axes 2/5 triggers, 6/7 hat are the xpad driver layout only. DualShock/DualSense (hid-playstation: 0 cross,1 circle,2 triangle,3 square,4 L1,5 R1,6 L2,7 R2,8 share,9 options,10 PS,11 L3,12 R3): triangle -> WEST bit, square -> NORTH bit (positional layout wrong), L2/R2 buttons -> BACK/MENU (pressing a trigger = Select/Start, so pause toggles), options -> LS, PS -> RS, share/guide -> MENU, buttons >=12 dropped (e.number<12 at line ~576). Switch Pro (hid-nintendo) is also different. style is always GENERIC (name only). Fix: SDL-style mapping DB keyed by vendor/product from evdev, fallback to xpad layout only for xpad devices.
E-L4. axes `/32767` (host_linux.c ~583) -> -1.00003; triggers on devices that report 0..max not -max..max (some pads use axis 2/5 0-based) read half scale: line ~589 `(v+1)*0.5`.
E-L5. d-pad: hat axes 6/7 thresholded at 0.5 (fine), but pads whose d-pad is buttons (some 8BitDo D-mode, many generic) have those button numbers mapped to arbitrary bits.
E-M1. macOS/iOS (host_macos.m:646-692, host_ios.m:858-899): only controllers with extendedGamepad; GameController order not guaranteed stable (same index issue); no startWirelessControllerDiscovery, no GCControllerDidConnect/Disconnect handling (polled each read, which works); no shouldMonitorBackgroundEvents (pad dead when window not frontmost, may be intended). macOS also never sees DInput-only pads. buttonOptions/buttonMenu: pads without Options leave bit 6 permanently 0, so Select+Start (pause) is unavailable on them (e.g. some MFi) while the game's only other pause route is Escape/touch.
E-A1. host_android.c:112-135 + on_input: ONE pad for all devices (no AInputEvent_getDeviceId): two pads or pad+keyboard-dpad share state; pad.on is never cleared on disconnect (stuck on, stuck buttons, owner never released); only index 0, no name/style (always GENERIC "Controller", labels "Bottom/Right/..." rather than the pad's). Right stick on Z/RZ is right for Xbox/PS via Android; trigger axes ok. AKEYCODE_DPAD_* from a gamepad source are consumed as pad buttons (ok) but the same codes from a keyboard are not.
E-N1. Headless/replay: eng_input_sample returns before polling when `headless` (input.c:204) (not a defect, noted).
